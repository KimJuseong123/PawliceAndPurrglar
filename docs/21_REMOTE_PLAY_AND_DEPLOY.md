# 원격 플레이와 배포

목표는 **EC2에 올리고 브라우저로 접속**하는 것이다. 이 문서는 거기까지의 길과,
지금 당장 다른 네트워크에 있는 두 사람이 테스트하는 방법을 적는다.

## 1. 왜 UDP를 버렸나

**브라우저는 UDP 소켓을 열 수 없다.** WebGL로 가는 순간 UDP는 선택지가 아니다.
그래서 전송을 WebSocket으로 바꿨다 (`UnityTransport.UseWebSockets = true`,
`NetworkSessionController.TryApplyTransport`).

부수 효과가 두 개 있고 둘 다 이득이다.

- 데스크톱 빌드와 WebGL 빌드가 **같은 전송을 쓴다.** 한쪽에서 찾은 버그가
  양쪽에서 찾은 버그가 된다.
- **터널을 통과한다.** UDP는 포트 포워딩과 공인 IP가 필요하고 한국 가정용
  회선 상당수는 CGNAT라 공인 IP가 없다. TCP 모양의 프로토콜은 무료 터널을
  그냥 지나간다.

## 2. 지금 상태

| 항목 | 상태 |
|---|---|
| 전송 | WebSocket (포트 기본 7979) |
| 호스트 리슨 | `0.0.0.0` — 밖에서 들어오는 연결을 받는다 |
| 클라이언트 주소 | **호스트명 허용.** `wss://`·`tcp://`·뒤의 `/경로`·`:포트`를 벗겨낸다 |
| 전용 서버 | **있음.** `-dedicatedServer`로 켠다 |
| WebGL 빌드 | 타깃은 있다 (`Build WebGL Playtest`). 접속 주소 주입은 아직 없다 |

실측: 2프로세스 `full` 시나리오가 WebSocket에서 양쪽 `passed=True`,
클라이언트가 `-netAddress localhost`로 **이름을 통해** 붙어 한 판을 끝냈다.

## 3. 지금 둘이서 테스트하기 (터널)

호스트 쪽에서:

```bash
ngrok tcp 7979
```

`tcp://0.tcp.ngrok.io:12345` 같은 주소가 나온다. 상대는 로비의 주소칸에
**호스트명만**, 포트칸에 **터널이 준 포트**를 넣는다.

```text
주소: 0.tcp.ngrok.io
포트: 12345
```

주소칸에 `tcp://0.tcp.ngrok.io:12345`를 통째로 붙여넣어도 된다 — 스킴과 포트를
벗겨낸다. 다만 **포트는 포트칸이 정한다.** 주소 안의 포트를 조용히 따르면
포트칸이 거짓말을 하는 칸이 된다.

### 주의

- ngrok은 계정과 authtoken이 필요하다. 무료 티어에 TCP 터널이 있다.
- **Cloudflare의 무료 quick tunnel(`trycloudflare.com`)은 HTTP 전용**이라 이
  용도에 맞지 않는다. TCP를 쓰려면 양쪽에 `cloudflared`가 필요하다.
- 방 목록 자동 발견은 UDP 브로드캐스트라 **터널 너머에서는 안 뜬다.** 주소를
  직접 입력해야 한다. 이건 EC2에서도 같다.
- 터널은 왕복 지연을 더한다. 조작감이 LAN보다 무겁게 느껴지면 터널 탓일 수
  있으니, 같은 공유기에서 한 번 비교해 보고 판단한다.

## 4. EC2로 갈 때 남은 일

이번 변경이 없앤 것: 전송 방식 결정, 호스트명 접속, 밖에서 들어오는 연결.

남은 것:

1. ~~전용 서버 모드~~ **완료 (2026-08-05)**. 아래 6절 참고.
2. **리눅스 헤드리스 빌드.** 메뉴는 만들었다 (`Build Linux Dedicated Server`).
   **이 PC에 Linux Build Support가 없어 아직 산출물이 없다** — Unity Hub의
   6000.5.4f1 톱니 > Add modules > Linux Build Support (IL2CPP)를 깔면 그대로
   돈다. 지금 깔린 모듈은 `WebGLSupport`와 `windowsstandalonesupport`뿐이다.
3. **WSS.** 브라우저는 `https://`로 받은 페이지에서 `ws://`로 접속할 수 없다.
   EC2 앞에 nginx나 Caddy를 두고 TLS를 끝내고 뒤로는 평문 WS로 넘긴다.
   도메인과 인증서가 필요하다 (Let's Encrypt).
4. **WebGL 클라이언트의 접속 주소.** 지금은 로비에서 손으로 넣는다. 배포본은
   자기가 받아온 도메인으로 자동 접속하는 편이 낫다.
5. **보안 그룹.** 게임 포트(또는 WSS 443)만 연다.

우선순위는 1 → 2 → 3이다. 1과 2 없이는 EC2에 올릴 것이 없고, 3 없이는 브라우저가
붙지 못한다. 4는 편의이고 5는 마지막이다.

## 5. 되돌리는 법

UDP로 돌아가려면 `TryApplyTransport`의 `UseWebSockets = true` 한 줄을 지우면
된다. 다만 그러면 브라우저 접속은 불가능해진다.

## 6. 전용 서버 (2026-08-05 추가)

```bash
PawsAndLoot.exe -dedicatedServer -netPort 7979
```

호스트와 다른 점은 하나다: **여기서는 아무도 플레이하지 않는다.** 두 캐릭터가
모두 클라이언트 소유이고, 판정하는 권한은 화면 없는 기계에 있다. 배포된 서버가
그래야 하는 모양이고 호스트는 될 수 없는 모양이다.

인자가 없으면 아무 일도 하지 않는다. 스스로 판단하는 빌드였다면 더블클릭이
전부 헤드리스 서버가 되고 플레이어에게는 열리지 않는 창만 남는다.

### 역할 배정이 바뀐 곳

`NetworkRoleBoard`는 스폰될 때 **자기 자신을 경찰로** 잡고 있었다. 호스트에서는
맞지만 서버에서는 그 자리에 사람이 없어서, 경찰 역할이 빈 의자에 배정되고
경찰관이 영원히 움직이지 않는다. 서버일 때는 **첫 번째로 들어온 클라이언트**가
가져간다. 한 번만 정해지므로 두 번째 클라이언트가 뺏지 않고, 재접속이 진행 중인
경기의 역할을 뒤섞지 않는다.

접속 인원 제한은 손댈 필요가 없었다. 접속한 클라이언트를 세는데 호스트에서는 그중
하나가 호스트 자신이므로, 로컬 플레이어가 없으면 같은 산수가 두 명을 받는다.

### 실측

서버 1 + 클라이언트 2로 돌렸다. 클라이언트 결과:

```text
sessionMode = Client
rolesAssigned = True
localRole = Police
policeClientId = 1
passed = True
```

`policeClientId = 1`이 요점이다. 서버는 0이고 플레이어가 아니며, 경찰은 첫 번째
사람에게 갔다. 호스트 모드 2프로세스 회귀도 그대로 양쪽 `passed=True`다.

### 리눅스에서 돌릴 때

```bash
./PawsAndLoot.x86_64 -dedicatedServer -netPort 7979
```
